# Chapter 12: Known Steps Take a Chain; Unknown Ones an Agent

**Summary**: *Two systems can be built on one model, one tool set and one goal, and still differ entirely in who decides what happens next. Lean too far toward autonomy and you pay a model call to reach a conclusion somebody reached years ago, on a bill that runs to fifteen times a chat once the work fans out. Lean too far the other way and the design fails on the first input that does not fit the route it was handed. This chapter is the architecture arranged around one question: what is genuinely not known before the run starts.*

## Every Step You Can Write Down in Advance Is a Step No Model Needs to Choose

A team wants an assistant for their **code review**. The **sequence is already settled**, because humans have been **running it by hand** for **two years**. Pull the diff. Check it against the house style rules. Look for tests that should have moved and did not. Summarise what changed. Post the summary.

**Five steps**, same order, every time. Now **write them down**.

That act **settles the architecture**. When the **sequence is knowable** before the input arrives, a **chain of prompts** is **cheaper, reproducible and inspectable** at every stage. Each stage takes one input and produces one output. Run it twice and the request travels the same route both times. Something breaks and the stage that broke has a **name and a fixture** you can rerun.

Hand those five steps to an agent instead and the first thing it does is **burn a model call** working out **which one comes first**. That call has **exactly one job**. It reaches a **conclusion the team reached** two years ago. You pay tokens for it, you pay a round trip for it, and you accept that Tuesday's run may reach a different conclusion.

Call this the **enumeration test**. Can you write the sequence down before the input arrives? If you can, **code holds the plan** and the model does the work inside each step. If you cannot, the **model holds the plan** and your **code holds the limits**. Anthropic draws the same line by asking where control flow lives: a workflow runs models and tools along **paths fixed in code**, while an agent **directs its own process** and keeps control of how the task gets done.<sup>[1]</sup> Control flow is the **whole question**.

The test has a second use, and it is the one scenarios reach for. Run it on **each workload separately** rather than once on the whole system. A **dependency review** that **follows fixed rules** and a **debugging assistant** that **explores unknown code** answer the test differently, so they should **not share a structure**. Force both through one checklist and investigations march through steps that do not apply. Give both an adaptive planner and every dependency review pays for a decision the rules already made. **One structure**, **two badly served workloads**.

The enumeration test is **not an argument for simplicity**. It is an argument about where a **decision gets made**. A step whose content is **genuinely hard**, needing judgement over **ambiguous input**, still belongs to the model. What belongs in code is the part nobody was ever unsure about: **which step follows which**.

## Five Workflow Shapes, Each Selected by a Different Thing the Task Leaves Open

The **named patterns** get taught as a **catalogue**. That is the wrong shape for using them. Sort them instead by what the **run does not know** when it begins, because that is the property a **scenario actually states**.

| What is unsettled when the run begins | The shape that answers it | What it buys, and what it charges |
|---|---|---|
| Nothing. The order is fixed and each step consumes the last one's output | A chain of calls, one per step | Every call gets an easier job, so accuracy rises. Latency is the sum of the steps |
| Which of a known set of categories this input belongs to | A classifying call in front of handlers written per category | Each handler is tuned for one case. A misclassification sends the request down the wrong branch |
| Nothing, and the parts do not depend on each other | The parts issued at once and joined afterwards | Elapsed time falls toward the slowest part. Every part is still billed |
| Nothing, but one pass is not trustworthy on its own | The same job run several times and the answers reconciled | Confidence from agreement. Cost scales with attempts |
| Which subtasks the input even requires | A coordinating call that decides the split, workers that run it, a synthesis pass | Decomposition that fits the input. A coordinator you now have to govern |
| How many rounds it takes to meet a written standard | A producing call and a critiquing call, looping | Measurable improvement per round, where criteria are explicit. Rounds without a cap |

Those are **prompt chaining**, **routing**, **parallelisation** in its two variants, **orchestrator-workers**, and **evaluator-optimizer**. Anthropic attaches a **selecting condition** to each one, and the conditions are worth holding as **tests** rather than as descriptions.<sup>[1]</sup>

Chaining wants a task that **splits cleanly into fixed subtasks**. It **trades latency for accuracy** by giving every call less to do. Routing wants two things at once: categories that **genuinely deserve separate handling**, and **classification you can trust** with the routing decision. Miss the second and the whole arrangement degrades, because a misrouted request gets handled well by the wrong specialist. Bad classification **poisons every branch**. Parallelisation **splits on independence** when the goal is speed and **repeats one job** when the goal is confidence. Evaluator-optimizer wants written criteria and a demonstrable gain from another round. The honest signal that it fits: a **human articulating feedback** measurably improves the output.

Orchestrator-workers sits on this chapter's boundary and is worth marking as such. The other four have their **control flow written down**. This one **hands the decomposition** itself to the model, because the subtasks **depend on the specific input** and cannot be fixed in advance. The **model decides the split**. Everything later in this chapter about coordination, **budgets and handoffs** starts applying the moment you choose it.

## An Agent Earns Its Cost Where Later Steps Depend on What Earlier Steps Find

Debugging an **unfamiliar system** is the case **autonomy was built** for. The reason is **structural** rather than a matter of difficulty. Nobody can write that investigation down in advance, because the **third thing worth checking** depends entirely on what the **first two returned**. A stack trace points at a module. Reading the module **rules out the obvious cause** and raises a different one. The next tool call exists because of that result and would never have been chosen otherwise. The **path is discovered, not planned**.

That is the property to look for, and it is narrow. A **later step that exists** because of an **earlier finding** is what **adaptivity buys**. **Variability** in the input alone does not qualify. A known set of variations is a **routing problem**.

The loop itself is short enough to hold in one sentence. The model is handed the request along with its **standing instructions**, its tool schemas and whatever history exists. It either answers or asks for a tool. The tool runs and the result goes back. The **cycle repeats** until a response arrives carrying **no tool calls**.<sup>[2]</sup> **Ground truth from the environment** at each step is what makes the **next decision better than a guess**.<sup>[1]</sup> An agent on a task with **no observable feedback** has nothing to adapt to. **Feedback is the fuel**.

What arrives with the loop is the part scenarios test. The **route through the work** is now produced by the model reasoning over whatever has piled up, rather than by **branching logic** a reviewer can read line by line. **Operational logs stop being enough**, because the interesting decisions happen inside a **transcript**. **Errors compound**: a **wrong turn** at step four is the input to step five. And the loop will **not stop on its own** unless you tell it how.

So **exit conditions** belong in the design, and they must not depend on the **model volunteering to finish**. The SDK gives you **two caps** that hold without cooperation. A **ceiling on tool-use round trips**, and a **ceiling on spend**, each returning its own **error subtype** so your code can tell a finished task from a **truncated** one.<sup>[2]</sup> Anthropic pairs autonomy with a **maximum iteration count** for the same reason.<sup>[1]</sup> A run that stopped because it **ran out of turns** and a run that stopped because it was done look identical in a log that records only the last message.

Two **named anti-patterns** sit either side of this. Both **read as competence**.

**Autonomy bought on a settled sequence** is the commoner one. Somebody reaches for an agent because agents are the interesting architecture, on a task whose steps a colleague could **recite from memory**. Every run pays for a **planning call that decides nothing**, and every run differs from the last with no gain in what the system can do. You **bought variance** and nothing else.

A **fixed checklist imposed on an investigation** is the mirror. It presumes the **order of inquiry is known**, which is precisely what an unfamiliar system denies. You watch an assistant march through irrelevant steps while the actual lead goes uninvestigated.

Anthropic's advice on where to start is blunt, and it survives contact with production. **Optimising a single call** with retrieval and **worked examples** is enough for many applications. Add structure only where the **simpler shape demonstrably fails**.<sup>[1]</sup>

## The Choice Is Made Per Path, So One System Can Hold a Chain and a Loop

The **two patterns** get argued as though a system has to be one or the other. **Most systems** that **reach production** are not.

Look at what the enumeration test is actually asked about. It is a question about a **route through work**, and a **single application** routinely carries **more than one route** with different properties. Invoices are the clean case. **Ninety-odd percent** of them arrive in a shape somebody has **already written down**, move through the same extraction and the **same validation every time**, and would gain nothing from a **model choosing the order**. The **remainder arrive malformed**, and what happens next is a **real decision** among several live options: send it back, ask the submitter, escalate to a person. **Nobody can say in advance** which applies, because that depends on what the malformation turns out to be.

Run the test on **each route separately** and both answers are obvious. Run it once on "the invoice system" and whichever answer you get is **wrong for half the traffic**.

So the shape that fits is a **coded sequence for the settled route** with a **model-driven step** invoked at the one point where the **route forks unpredictably**. That is not a compromise between two architectures. It is the **same rule applied twice**, and it is what Anthropic's own advice implies: **start simple**, and add structure only where the simple shape is demonstrably failing.<sup>[1]</sup> Demonstrably failing is a **property of a path**, not of a product.

The **whole-system pattern choice** is the anti-pattern, and it produces both of this chapter's **named errors at once** from a single decision. Pick the loop and the settled route **pays a planning call** on every invoice to decide something that was **never open**. Pick the chain and the exception **falls through a branch** nobody could write. The **traffic profile** is what tells you how much each mistake costs, and it is usually in the logs already.

## A Coordinator Owns the Budget, the Validation and the Contract at Every Handoff

A **manager or supervisor hierarchy** is one agent that **decomposes a request** and **delegates the pieces** to specialists. Each specialist holds a **separate conversation**, a tool list of its own, and a **history nobody else reads**. The managed-agent surface makes it concrete. Every agent carries its own model, system prompt, tools, connected servers and skills, and each runs in a **context-isolated thread** with its own event stream. Tools, servers and context are **shared with nobody**.<sup>[3]</sup>

**Three properties** of that arrangement **decide scenarios**. None of them shows up in a diagram.

**Delegation goes one level**. A coordinator calls the agents on its roster, and an agent that is itself a coordinator cannot go on that roster; the attempt **fails validation**.<sup>[3]</sup> Depth is a **configured limit** rather than an open tree, so the hierarchy stays **shallow by construction**. The SDK exposes the same idea as a **depth cap**, **three layers** below the main conversation by default and **settable down to none**.<sup>[4]</sup>

**Threads persist**. A coordinator can send a **follow-up** to an agent it already used, and that agent still holds everything from its **earlier turns**.<sup>[3]</sup> Delegation is **not necessarily one-shot**, which is what makes a **review loop** possible.

**Spend is pooled**. A **session budget** is a **single cap** shared across every thread, and threads **pause independently** as it is reached.<sup>[3]</sup> On the SDK side, subagent spend counts toward the query total, and once the cap is hit the **next spawn fails** outright.<sup>[2]</sup>

Now the failure mode, because it is the one the exam tests hardest. **Delegation without governance** is an orchestrator that **hands out work** and **accepts whatever comes back**. It looks like an architecture and behaves like a **mailing list**. Subtasks return in **incompatible shapes**. One worker's **malformed output** becomes the next stage's input. Contradictions between workers **never get reconciled**, and the first human to notice is a user reading the final answer. **Nothing checked anything** on the way.

The repair is **enforcement at the point of handoff**, in three parts. A **budget per subagent**, so no single worker can consume the run. Validation of each result against a **defined shape** before it moves on, so a malformed return stops where it was produced. And an **explicit contract per handoff**, so both sides agree what a **finished subtask** contains.

Two plausible alternatives fail for reasons worth naming. **Retries plus a shared trace** improve recovery and make the **postmortem easier**, while **intercepting nothing** on the way downstream, which is precisely the failure described. Letting workers see each other and **negotiate their differences** asks them to settle contradictions among themselves and **deletes the component** whose job that was. **Collapsing** everything back into **one call** is the third, and it **abandons the isolation** and the parallelism you built the architecture for rather than managing them.

Delegation detail is the other half of what a coordinator owns. Anthropic's research system found that subtasks handed out as **short instructions** produced agents that **misread the assignment** or **repeated each other's searches**. The repair was to give every subtask an **objective**, an **output format**, guidance on which **tools and sources** to use, and **boundaries** saying where it stops.<sup>[5]</sup> That system also encodes how much **effort a query deserves**, directly in the **coordinator's prompt**. A **simple lookup** gets one agent and a handful of tool calls. Genuinely broad research gets many more.<sup>[5]</sup> Without the scaling rule, the observed behaviour was **dozens of agents spawned** for questions that needed one.

## Fifteen Times the Tokens of a Chat, and Parallel Exploration Is What Buys It Back

The numbers are published and they are not small. An agent uses roughly **four times the tokens** of a chat interaction. A **multi-agent system** uses roughly **fifteen**.<sup>[5]</sup> Every worker **holds its own context** and spends its own tokens against it, so the multiplier lands on input and output alike. Every **context is paid** for.

Set that beside what the architecture delivered. A system running Claude **Opus 4 as the lead** with **Claude Sonnet 4 workers** beat a single-agent Claude Opus 4 baseline by **90.2%** on an internal research eval. Anthropic's analysis attributes most of that **performance variance** to **token spend**.<sup>[5]</sup> The shape works largely because it buys more **parallel computation**. That is a real gain. It is also the **whole invoice**.

So the qualifying condition is narrow. **Fan-out earns the multiplier** on work that genuinely splits into parts nobody has to wait on: research across many **separate sources**, material **larger than one context window**, a surface with **many complex tools**.<sup>[5]</sup> The disqualifying conditions are just as specific. Tasks where every agent needs the **same context**. Domains with **heavy dependencies** between the pieces. And **most coding work**, where each step consumes the last one's result and there is little left to explore in parallel.<sup>[5]</sup> Later Anthropic research sharpens the edge. **Moving context between agents** costs about as much as acting on it, so coordination is **nowhere near the cheap part** of the design.<sup>[6]</sup>

**Fan-out on a dependent chain** is the anti-pattern, and it usually arrives as a **latency fix**. Work that ran slowly gets split across **parallel workers** on the reasoning that simultaneous work finishes sooner. **Elapsed time barely moves**, because the pieces were waiting on each other all along, and the **bill multiplies**. Splitting a sequence does **not make it parallel**. You get a sequence with more contexts in it.

There is a **control cost** the arithmetic does not show. Every worker you add is another point at which the **run can break**. The **retriable-versus-terminal decision**, the backoff and the fallback all have to be **wired into each one separately**. A single worker meeting a **rate limit** with nothing to back off with can hold the compilation step open while the coordinator waits for a return that never arrives. Orchestration does **not replace failure handling**. It **multiplies the work**.

Two levers reduce the multiplier without abandoning the shape. Run the coordinating agent on a **capable model** and the **workers on cheaper ones**, so top-tier rates are not paid across every parallel context. And keep the **roster honest**: independent agents pointed at **genuinely separate territory** have been observed returning **largely different findings**, which is the return the split was supposed to produce.<sup>[6]</sup> **Overlapping workers** are **money spent twice**.

## A Subagent Starts Empty, So Whatever the Next Stage Needs Has to Be Written Into the Prompt

**Isolation** is the property that makes **delegation useful**. It is also the property that **breaks handoffs** when a designer forgets it holds.

A **subagent** that is **not a fork** begins with **no parent conversation**. The only content crossing from parent to child is the **prompt string** on the call that launched it. File paths, error text and decisions already taken are present because **somebody put them** there.<sup>[7]</sup> **Nothing arrives by inheritance**. Going the other way, intermediate tool calls and results stay inside the child and only its **final message returns**.<sup>[7]</sup> A worker can read dozens of files and the caller's window **grows by a summary**. Chapter 7 owns that trade as a context technique. Architecturally what matters is the consequence: **nothing crosses unless something carries** it, in either direction.

**Constraints inherit unevenly**, and that is where a design gets caught. **Skills do not carry** over to a delegated task, so a worker depending on a specific instruction set needs it registered against that worker. **Permission scope does carry** over and is not reset at the boundary. **Project-level context files load**, while the parent's own conversation, its invoked skills and its already-read files do not.<sup>[8]</sup> A **standing preference** you stated once in the main conversation has to be **restated in the delegation prompt** to reach the agent doing the work.

Which is why handoffs get **recorded rather than narrated**. The stage that **observes a detail** is the stage that **writes it down**, because no later stage can recover a **line range nobody kept**. A coordinator that collects three workers' findings and asks a synthesis stage to **attribute claims to files** is asking for facts that stage never saw. Guessing is where a claim gets attached to the wrong file. The repair is a **structured record** produced at the **point of observation**: path, symbol, line range, and the snippet standing as evidence.

Two named alternatives fail instructively. **Concatenation offered as integration** hands the synthesiser every transcript and **imposes no structure** at all. Attribution then gets worked out a **second time downstream**, when it was free the first time. **Regular expressions over summaries** extract whatever a summary happened to mention. Every **omission stays omitted** and reads as an absence of findings.

Sequencing between stages needs the same treatment. A report stage that **runs before its source stage** has finished produces **claims nobody can check**, and three repairs suggest themselves while one works. **Generating first and pruning afterwards** leaves a report whose shape was set by claims that could never be checked. Asking the report stage to hold off requires it to observe a state it cannot see. Scanning a message for the right words reads **done-ness out of prose**. **Block the downstream stage** on an **explicit signal the producing stage sets**, a status plus a **structured manifest** of what it produced, and the ordering then rests on a fact.

Coverage is the same argument one level up. When output reads coherently but **one region is thin**, more effort aimed the same way **re-samples the same blind spot**, and a **higher fixed iteration count** spends more without pointing it anywhere. Effort has to be aimed. What closes a gap is an explicit **check against the intended scope**, plus a route for acting on whatever it finds missing: a coordinator review that **names the thin region**, **dispatches follow-up work** at it, and **reruns the synthesis**. Hosted sessions formalise this as a **defined outcome** with a rubric. A **grader** evaluates the artifact in a **separate context window**, precisely so the implementation choices it is judging cannot influence it. Its explanation goes back for the next round.<sup>[9]</sup>

## Memory Is a Design-Time Decision About What Survives the Session

An agent loop ends and everything it accumulated ends with it. What the next session knows is a choice you make at **design time**. Call that choice the agent's **memory scope**. The two ways of getting it wrong pull in **opposite directions**. Too much state carried in the conversation **inflates every call**, because the whole history gets **re-read on every turn**. Too little written down anywhere **strips the agent of continuity**. **Whatever nobody recorded** is gone the moment the **session closes**.

| Scope | What is still there next session | What it costs | What it drops |
|---|---|---|---|
| Held in the conversation | Nothing. State survives turns, not restarts | No retrieval work; token cost grows with every turn | Everything, on a new session or a clear |
| Written to external storage | Whatever was written, readable across sessions, users and instances | Retrieval latency, plus the read and write logic to maintain | Nothing on the persistence side |
| Condensed and reinjected | A summary of the prior conversation | Less per session than replaying history in full | Any detail the summariser did not think to keep |
| Nothing kept | Nothing, by design | No overhead at all | Everything from earlier sessions |

The trap is that the first row **prototypes beautifully**. History goes in the message list, the list goes up on every call, and it works for a while. Then **cost scales with session length** and **latency climbs** as the window fills. The fix is a refactor that is mechanically simple and arrives at the **worst possible moment**. Under production pressure, on a deadline already running. **Deciding at design time** costs an afternoon. Deciding under **pressure costs a release**.

The managed platform gives the external row a documented shape. A **memory store** is a collection of documents **mounted into the session** as a directory. The agent reads and writes it with the **same file tools** it uses for everything else, and a note in the **system prompt** says where to look. Every change creates an **immutable version**, so you get an **audit trail** and a **point-in-time recovery** path. Access can be **granted read-only** where a session should consume **shared reference material** without adding to it.<sup>[10]</sup>

**Resumability** separates memory from persistence proper, and it is a different requirement rather than a stronger one. A task running for half an hour with **defined intermediate points** needs state that **outlives the process** computing it, so an interrupted run reloads from the **last completed point** instead of starting over. A **longer timeout makes interruption rarer** without making it **survivable**. A **duplicate copy** running alongside **doubles the cost** and loses both to any interruption they share. Anthropic reaches the same conclusion operationally. **Restarts are expensive**, so the answer pairs the model's adaptability with **deterministic retry logic** and **regular checkpoints** that let a run resume from where the error hit.<sup>[5]</sup>

## A Framework Wraps the Same Loop and Charges in Visibility

**Agent frameworks** exist because the loop has a **shape everybody rebuilds**. Strands, LangGraph and PydanticAI belong to a category that also holds **Anthropic's own SDK**. The category earns its place by handling the parts that are **identical in every implementation**: calling the model, defining and parsing tools, chaining calls together.<sup>[1]</sup> Nobody should **write those twice**.

What they **charge is visibility**. Anthropic is direct about the tradeoff. Those layers can **obscure the prompts and responses** underneath, which makes debugging harder. **Wrong assumptions** about what sits below the abstraction are a **common source of error**. The recommendation is to start against the **model API directly**, because many of these patterns run to a few lines of code.<sup>[1]</sup> Use a framework and you should **understand its internals**. Moving into production, **reducing abstraction** is a legitimate direction of travel rather than a regression.

Underneath the framework question sits a different one: who **runs the loop**. Write it against the **Messages API** and you own every **iteration and every exit condition**. An SDK runs the same loop **inside your process** and supplies tool execution and iteration structure. A **hosted agent service** runs the loop and the sandbox elsewhere. The agent is defined once as a **versioned resource**, and events go in from your application while **results stream out**.<sup>[11]</sup> Chapter 13 owns that choice and what each path leaves you holding.

One thing holds across all of them. A framework decides how much of the loop **somebody else maintains**, and it has **no opinion** about whether the task **needed a loop** at all. One scale point is worth carrying, because it is the same argument in different clothes. When orchestration grows past what a **single conversation can coordinate**, moving the **plan into a script** the **runtime executes** keeps the **branching and the intermediate results** out of every context window. The conversation receives only the **finished answer**.<sup>[12]</sup> That is the **enumeration test** again, aimed at the coordination rather than at the task.

## How Wrong Answers Are Built on This Material

Wrong answers here **name real architectures**. None of them is stupid. Every one describes something a **competent team has shipped**, which is why reading for **obvious nonsense finds nothing**. What separates them is a **single assumption underneath**, and **four assumptions** produce nearly all of them.

- **Autonomy offered where the sequence was already settled**. The option lets the **model plan a path**, on a scenario describing steps as **repeatable**, fixed, or **already run by hand**. It is **not a weaker answer** than the chain; it **pays a model call** to decide something the scenario **stated as decided**. It becomes correct only when the scenario says the **path depends on what earlier steps find**.
- **Isolation assumed away**, or **paid for and then discarded**. Options that treat **separate agents** as **sharing a conversation**, that **forward every prior message** to every agent, or that **delete the coordinating component**. All three deny the property that makes **delegation worth its cost**. The **design question** at a handoff is never whether a **fact is visible**. It is what **gets passed**.
- **Coordination replaced by observation**, by **negotiation**, or by **cleanup**. **Tracing, retries and dashboards** intercept **nothing on the way downstream**. **Peer-to-peer reconciliation** asks workers to settle **contradictions the coordinator exists** to settle. **Generating output** and **pruning it afterwards** leaves the structure shaped by **claims that never held**. Each is a **real practice aimed** one step away from the stated failure.
- **Capacity or effort offered** where **structure is the problem**. A **larger window** against **interleaved sub-problems that already fit**. A **higher iteration count** against a **coverage gap** that more of the same effort will **re-sample**. A **longer timeout** against **interruptions that need surviving** rather than avoiding. **Name the quantity the option changes**, then check whether the scenario named that quantity.

**Match on what the scenario** is doing rather than on the **industry it is dressed** in.

| When the scenario says | The answer is usually | The trap is usually |
|---|---|---|
| The steps are repeatable, known, or already run by hand | A fixed sequence of prompts, one per step | Letting the model plan a route that is already decided, or randomising it |
| The correct path is unknown at the start and depends on what is found | Planning that adapts to each discovery, carrying findings forward | A fixed checklist, ignoring intermediate results, or restarting when a lead dies |
| One system holds a stable-rule workload and an open-ended one | Different structures, split on whether the next step is known in advance | One structure imposed on both, in either direction, or one large prompt for everything |
| Findings reach a later stage attached to the wrong file, or missing detail | A structured record written where the observation was made | Concatenating transcripts, pattern-matching summaries, or asking the last stage to reconstruct it |
| A later stage runs before an earlier one has finished | Block it on an explicit status and manifest the producing stage sets | Inferring completion from prose, or generating first and pruning after |
| A top component interprets requests and subordinates keep their own histories and tools | A coordinator with per-subagent isolated context | Reading it as one shared history, as a pipeline, or as retrieval from an index |
| Workers return contradictory or malformed output that moves downstream anyway | Per-worker budgets, schema validation before the handoff, explicit contracts | Retries plus a shared trace, peer negotiation, or collapsing to a single call |
| One request interleaves several unrelated sub-problems and progress gets lost | One worker per sub-problem, with completion tracked by the coordinator | A larger window, or asking the agent to keep its own running tally |
| Output is coherent but one region of the material is thin | A coverage check against what should be there, plus targeted follow-up work | Repeating the broad assignment, raising the iteration count, or hiding the thin section |
| Subtasks have different success criteria and one may hand work back | A state-driven structure with defined transitions between subtasks | A linear chain with no return path, or one loop holding every tool |
| A task runs for tens of minutes and has named intermediate points | State persisted at each point and reloaded when the run resumes | A longer timeout, or a duplicate copy running in parallel |
| Cost multiplied after a fan-out and the answers barely improved | Check whether the pieces were ever independent; a single agent may fit | Treating parallel workers as a latency fix, or adding more of them |
| One flow has a routine majority and a small unpredictable remainder | A coded sequence for the routine path, with the model invoked only where it forks | Any option choosing one pattern for the whole system, in either direction |

One habit does more than the table. Before comparing options, name what the scenario says is unknown when the run begins, and what it says is already settled. Almost every wrong answer here moves a decision to the wrong side of that line.

## What to Remember

- The **enumeration test**: can the **sequence of steps** be **written down before the input arrives**? If it can, **code holds the plan** and the model works inside each step. If it cannot, the **model holds the plan** and **code holds the limits**: turn caps, spend caps, validation.
- **Workflows run models and tools** along **paths fixed in code**; an **agent directs its own process** and decides how the task gets done. Same model, same tools, different owner of the next decision.
- **Five workflow shapes**, each **selected by what the run does not know**: **chaining** for a fixed ordered split, **routing** for known categories needing separate handling, **parallelisation** for independent parts or for repeated attempts, **orchestrator-workers** when the subtasks themselves depend on the input, **evaluator-optimizer** when criteria are written down and another round measurably helps.
- **Adaptivity is warranted** only where a **later step exists** because of what an **earlier one found**, which is why an unfamiliar system is the canonical case. **Variable input alone is a routing problem**, not a reason for autonomy.
- An **agent loop does not stop on its own**. Exit conditions belong in the design, enforced by a **maximum turn count and a spend ceiling** returning distinct error states, never by the model choosing to finish.
- A **coordinator owns budget, validation and the handoff contract**: a **spend limit per worker**, **each result checked** against a **defined shape before it moves** on, and an **agreed definition of a finished subtask**. **Tracing and retries** intercept **nothing on the way downstream**, and **peer negotiation deletes the component whose job** it was.
- **Delegated subtasks need an objective**, an **output format**, **named tools and sources**, and a **boundary**. Short instructions produce workers that misread the assignment or repeat each other's work.
- A **multi-agent system costs roughly fifteen times a chat** and an **agent roughly four**, because every **worker spends its own tokens** on its **own context**. The multiplier is bought back **only by genuine parallel exploration**: separate sources, material larger than one window, many tools. **Tightly coupled work pays the fan-out** and collects **no parallel benefit**.
- **Fan-out multiplies failure sites**, so **retry, backoff and fallback** apply to each **worker separately**. One stalled worker can hold the synthesis step open indefinitely.
- A **subagent starts with no parent conversation**: the **launching prompt is the only channel** in, and **only its final message returns**. **Skills do not carry** over to a delegated task, while **permission scope** does.
- **No later stage** can **recover a fact nobody recorded**, so **whichever stage sees a detail writes it down**: **path, symbol, line range, evidence snippet**. **Sequencing rests** on a **status the producing stage sets**, never on words found in its prose.
- **Memory scope is decided at design time**: **in-conversation** state dies at the session boundary, **external storage** survives across sessions and users at the price of retrieval latency, **summarisation** keeps only what the summariser chose, **stateless** keeps nothing by design. **Resumability needs state outliving the process**; a longer timeout only makes interruption rarer.
- **Frameworks wrap the same loop** and **charge in visibility**, obscuring the prompts and responses underneath. Start against the model API directly, understand what a framework does below its abstraction, and **reduce layers moving into production**.
- The **pattern choice belongs to a path**, **not to a system.** Run the **enumeration test on each route separately**: a **settled route takes code**, and a **model-driven step belongs** only where the **route forks unpredictably**. One decision made for the whole product **produces both named errors at once**, paying for planning on the settled majority and having no branch for the exception.
